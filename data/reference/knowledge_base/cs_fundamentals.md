### Python GIL（全局解释器锁）

**结论：** GIL 是 CPython 的机制，同一时刻只有一个线程执行 Python 字节码。

**影响：** CPU 密集型多线程无法利用多核；IO 密集型多线程不受影响（IO 操作会释放 GIL）。

**解决方案：** 多进程（`multiprocessing`）、C 扩展释放 GIL、使用其他 Python 实现（Jython、IronPython）。

### TCP 三次握手

**过程：**
1. 客户端 → SYN → 服务器
2. 客户端 ← SYN-ACK ← 服务器
3. 客户端 → ACK → 服务器

**为什么是三次不是两次：** 防止已失效的连接请求到达服务器，导致服务器误开连接。两次握手无法验证双方收发能力均正常。

---

### TCP 四次挥手

**过程：**
1. 主动方 → FIN → 被动方
2. 被动方 → ACK → 主动方（被动方仍可发送剩余数据）
3. 被动方 → FIN → 主动方
4. 主动方 → ACK → 被动方（主动方等待 2MSL 后关闭）

**TIME_WAIT 状态：** 主动关闭方在发送最后一个 ACK 后等待 2 倍 MSL（Maximum Segment Lifetime），确保最后的 ACK 能到达对方，且网络中残留的旧连接报文全部消失。

### HTTP 与 HTTPS 的区别

**HTTP：** 明文传输，端口 80，无加密无认证。

**HTTPS：** HTTP + TLS/SSL，端口 443。通过证书验证服务器身份，传输内容对称加密，防窃听、防篡改、防冒充。

**TLS 握手流程：**
1. Client Hello（支持的加密套件 + 随机数）
2. Server Hello（选定加密套件 + 证书 + 随机数）
3. 客户端验证证书 → 生成 Pre-Master Secret → 服务器公钥加密发送
4. 双方用三个随机数生成对称密钥 → 后续通信加密

### 快速排序

**核心思想：** 分治。选一个 pivot，将数组分为小于 pivot 和大于 pivot 两部分，递归排序。

**时间复杂度：** 平均 O(n log n)，最坏 O(n²)（每次 pivot 都是最值）。

**空间复杂度：** O(log n)（递归栈深度）。

**优化：** 三数取中选 pivot、小数组用插入排序、尾递归优化。

---

### 归并排序

**核心思想：** 分治。将数组递归拆分为单元素子数组，再两两合并为有序数组。

**时间复杂度：** 稳定 O(n log n)，不受输入数据影响。

**空间复杂度：** O(n)（需要额外数组存放合并结果）。

**适用场景：** 外部排序、链表排序、需要稳定排序时。相比快排，归并排序是稳定的，但需要额外空间。

---

### 二分查找

**前提：** 数组有序。

**思路：** 每次取中间元素与目标比较，缩小一半搜索范围。

**时间复杂度：** O(log n)，空间 O(1)（迭代）或 O(log n)（递归）。

**变体：** 查找第一个等于目标的位置、查找最后一个小于目标的位置、旋转数组二分查找。

---

### 哈希表原理

**核心：** 数组 + 哈希函数。key 经哈希函数映射到数组下标。

**冲突解决：**
- 拉链法（Chaining）：每个槽位存链表/红黑树，冲突时追加节点。Java HashMap 超过 8 转红黑树
- 开放寻址法（Open Addressing）：冲突时按规则探测下一个空位。Redis dict 使用此方法

**负载因子：** 已用槽位 / 总槽位。过高时触发扩容（rehash），Java HashMap 默认 0.75。

---

### 红黑树

**性质：**
1. 每个节点是红色或黑色
2. 根节点是黑色
3. 叶节点（NIL）是黑色
4. 红节点的子节点必须是黑色（不能连续红）
5. 任意节点到叶节点的路径上黑色节点数相同

**用途：** Java TreeMap、C++ std::map、Linux CFS 调度器、epoll 事件管理。

**与 AVL 树对比：** 红黑树插入删除更快（最多 3 次旋转），AVL 查询更快（更严格平衡），红黑树更适合写多读少场景。

### 数据库索引

**B+ 树索引：** 所有数据存在叶节点，叶节点通过链表连接，非叶节点仅存键值用于导航。适合范围查询。

**哈希索引：** 等值查询 O(1)，不支持范围查询。MySQL Memory 引擎默认使用。

**聚簇索引 vs 非聚簇索引：** 聚簇索引（如 InnoDB 主键）的叶节点存整行数据；非聚簇索引叶节点存主键值，查询需回表。

**最左前缀原则：** 联合索引 (a, b, c) 中，查询条件包含 a → 走索引；仅含 b 或 c → 不走索引。

### 数据库事务

**ACID 特性：**
- **原子性（Atomicity）：** 事务要么全做要么全不做（Undo Log 回滚）
- **一致性（Consistency）：** 事务前后数据库从一致状态到一致状态
- **隔离性（Isolation）：** 并发事务互不干扰（MVCC + 锁）
- **持久性（Durability）：** 提交的事务永久保存（Redo Log）

**隔离级别：**
- 读未提交（Read Uncommitted）—— 脏读
- 读已提交（Read Committed）—— 不可重复读
- 可重复读（Repeatable Read）—— 幻读（InnoDB 通过 Gap Lock 解决）
- 串行化（Serializable）—— 逐事务执行，性能最低

### 进程与线程

**进程：** 资源分配的基本单位，拥有独立内存空间。进程间通信（IPC）：管道、消息队列、共享内存、Socket。

**线程：** CPU 调度的基本单位，同进程线程共享内存空间。线程同步：互斥锁、条件变量、信号量、读写锁。

**协程：** 用户态轻量线程，由程序自身调度而非操作系统。切换开销极小（纳秒级），适合 IO 密集型高并发。Go goroutine、Python asyncio、Kotlin 协程。

### Python 装饰器原理

**本质：** 一个接受函数作为参数并返回新函数的高阶函数。`@decorator` 语法糖等价于 `func = decorator(func)`。

**常用内置装饰器：** `@staticmethod`、`@classmethod`、`@property`、`@functools.wraps`（保留原函数元信息）。

**带参数的装饰器：** 外层再包一层函数，`@decorator(args)` 等价于 `func = decorator(args)(func)`。

### 设计模式 — 单例模式

**目的：** 确保一个类只有一个实例，并提供一个全局访问点。

**Python 实现：** 使用模块级变量（模块天然单例）、`__new__` 控制实例化、或使用装饰器/元类。

**适用场景：** 数据库连接池、配置管理器、日志记录器、线程池。

**注意：** 单例在多线程环境下需要加锁（双重检查锁定）；单例增加全局状态不利于测试和模块化。

---

### 设计模式 — 工厂模式

**简单工厂：** 一个工厂类根据参数返回不同产品实例。

**工厂方法：** 定义一个创建对象的接口，子类决定实例化哪个类。符合开闭原则。

**抽象工厂：** 创建一组相关或依赖的对象族，无需指定具体类。

**适用场景：** 数据库驱动切换（MySQL / PostgreSQL）、UI 组件库跨平台渲染、日志处理器选择。

### RESTful API 设计原则

**核心约束：**
- 资源导向：URL 表示资源（`/users/123`），HTTP 方法表示操作（GET / POST / PUT / DELETE）
- 无状态：每个请求包含全部所需信息，服务器不保存客户端会话状态
- 统一接口：使用标准 HTTP 状态码（200 OK、201 Created、400 Bad Request、401 Unauthorized、404 Not Found、500 Internal Server Error）

**最佳实践：** 版本控制（`/v1/users`）、分页（`?page=1&size=20`）、HATEOAS（响应中包含下一步可用的链接）。

---

### JWT 认证原理

**结构：** Header.Payload.Signature（三段 Base64URL 编码，用 `.` 连接）。

**流程：**
1. 客户端提交用户名密码 → 服务端验证 → 生成 JWT
2. 客户端存储 token（localStorage / cookie）→ 后续请求在 Authorization 头携带 `Bearer <token>`
3. 服务端验证签名 → 从 Payload 提取用户信息

**优点：** 无状态、跨域友好、去中心化验证。**缺点：** token 签发后无法主动失效（需配合黑名单/短过期+刷新 token）。

### Linux 常用命令

**文件操作：** `ls -la`（列出）、`find /path -name "*.py"`（查找）、`grep -r "error" /var/log/`（搜索文本）、`tail -f`（实时跟踪日志）。
